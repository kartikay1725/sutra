# SUTRA — Pull Request Architecture & Integration Guide (v0.3.1)

## Overview
This document defines the architectural specification for introducing Pull Requests (PRs) into SUTRA v0.3.1 while strictly preserving all established guarantees from SUTRA Production Gates 1–4.

The Pull Request layer is a **higher-level management abstraction** built directly on top of SUTRA's authoritative `Change` and `ChangeReview` architecture. It does NOT duplicate code operations, semantic diffs, review states, or conflict detection.

---

## Architectural Hierarchy & Data Flow

```
Git Client / Transport (HTTP receive-pack)
           │
           ▼
    GitPushEvent (Durable Event Queue in PostgreSQL)
           │
           ▼
     Worker Process (Lease Ownership + Crash Recovery)
           │
           ▼
     Change Model (Authoritative Code Operation)
    ├── operation_key (SHA-256 Idempotency)
    ├── ChangeFile & ChangeEvent
    └── Status: proposed | recorded | blocked | rejected
           │
           ├── Policy Evaluation (ChangePolicyService)
           │     ├── Risk Level Assessment
           │     ├── Conflict Analysis (ConflictService / Git merge-tree)
           │     └── Capability Checks (AuthorizationService)
           │
           ├── Human & Agent Approvals (ChangeReview)
           │     └── Authoritative Review Truth (pending | approved | rejected)
           │
           ▼
     PullRequest Model (Management & Lifecycle Abstraction)
    ├── Reference to source Change (source_change_id)
    ├── Repository, Author, Target Branch, Commits
    ├── Statuses: draft | open | approved | merged | closed | rejected
    └── Unique Active PR Boundary (UNIQUE(source_change_id))
           │
           ▼
     Merge Orchestration Boundary
    ├── Precondition Check: Policy (ALLOW/REVIEW), Review (APPROVED), Conflict (NONE)
    └── Guarded State Transition -> `merged`
```

## Core Invariants & Boundaries

1. **Change Authoritative Truth**: The `Change` record remains the single source of truth for the code operation, commit SHAs, file modifications, and `operation_key` idempotency.
2. **Review Truth Reuse**: Pull Requests delegate approval truth directly to `ChangeReview`. A PR cannot be merged if its underlying `Change` has unapproved or rejected reviews or violates self-approval constraints.
3. **Policy Boundary**: Pull Requests delegate policy checking to `ChangePolicyService`. A PR with a policy decision of `BLOCK` or unfulfilled `REVIEW` cannot be merged.
4. **Conflict Boundary**: Pull Requests delegate mergeability and file overlap analysis directly to `ConflictService`.
5. **Authorization Boundary**: Creation and lifecycle management of PRs require explicit authorization check via `AuthorizationService` for the target repository.
6. **PR Uniqueness Constraint**: Each `Change` is linked to at most one active Pull Request (`UNIQUE(source_change_id)` in database constraint) to prevent race conditions and duplicate PR pollution.

## Model Specification (`PullRequest`)

- `id`: `String(36)` Primary Key (UUIDv4)
- `repository_id`: `String(36)` FK -> `repositories.id` (ON DELETE CASCADE)
- `author_id`: `String(36)` FK -> `users.id` (ON DELETE RESTRICT)
- `source_change_id`: `String(36)` FK -> `changes.id` (ON DELETE CASCADE, UNIQUE)
- `title`: `String(255)` Non-null
- `description`: `Text` Nullable
- `target_branch`: `String(255)` Non-null
- `source_commit`: `String(64)` Nullable
- `target_commit`: `String(64)` Nullable
- `status`: `String(30)` Non-null, default `'open'`
  - **CHECK constraint**: `status IN ('draft', 'open', 'approved', 'merged', 'closed', 'rejected')`
- `created_at`: `DateTime(timezone=True)` Non-null
- `updated_at`: `DateTime(timezone=True)` Non-null
- `merged_at`: `DateTime(timezone=True)` Nullable
- `closed_at`: `DateTime(timezone=True)` Nullable

---

## Lifecycle State Machine

- `draft` -> `open`
- `open` -> `approved`
- `open` -> `rejected`
- `open` -> `closed`
- `approved` -> `closed`
- `rejected` -> `open`

Terminal states: `merged`, `closed`, `rejected`. No transitions out of `merged` are allowed.

---

## Known Limitations

1. **No Server-Side Git Merge Transport**: SUTRA currently has no safe server-side Git merge transport mechanism.
2. **Merge Orchestration**: `POST /v1/pull-requests/{id}/merge` evaluates all merge preconditions (approvals, policies, conflicts). If all checks pass, it returns `status = "merge_ready"`. It does **NOT** transition `pr.status` to `merged`, update `merged_at`, emit a `pull_request.merged` event, or modify Git refs.
